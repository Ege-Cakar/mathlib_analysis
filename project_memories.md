# MWM Project Memories

High-alpha facts for future Claude sessions. Read this first.

## TL;DR

The project explores "the geometry of Mathlib": treating Mathlib as a graph
where nodes = theorems/premises and edges = "this proof cites this premise".
Two questions are open:

1. **A → B paths** in the proof DAG (does there exist a chain of premise
   citations from B back down to A, and how long?). The simple version is
   already implemented — see "Pipeline" below.
2. **Predictive power of spectral coordinates**. Empirically (so far) the
   eigencoordinates of the normalised adjacency do NOT predict the top-level
   Mathlib category of a node. See "Negative result" below.

## Dataset and certified facts

Source: LeanDojo Benchmark 4, random split, located at
`Old/data/leandojo/leandojo_benchmark_4/random/{train,val,test}.json`.

Treat *only* LeanDojo `traced_tactics[*].annotated_tactic` premise hits as
real edges. Anything generated by a model is not certified until Lean accepts
it.

Graph stats (from `results/paths/dependency_stats.json`):
- 122,517 theorems indexed; 61,544 with traced tactics.
- 259,580 traced tactics → 418,704 premise occurrences → **309,396 unique
  directed edges** (matches the expected count we saw in earlier prep).
- 138,333 unique nodes (theorems + premises) with file/category metadata.
- The largest spectral-classification subgraph keeps 94,635 nodes (those that
  have `category != "UNKNOWN"` and degree > 0 after symmetrising).

Top categories by outgoing edge volume: Analysis (42k), Algebra (36k),
Data (34k), MeasureTheory (30k), RingTheory (25k), Topology (22k),
NumberTheory (19k), LinearAlgebra (16k), CategoryTheory (13k), Order (10k).

Top tactic heads on dependency edges: rw (83k), simp (53k), have (35k),
exact (31k), refine (18k), simp_rw (11k), simpa (10k).

## Pipelines

### `analysis/graph_geometry.py` — richer graph features (NEW 2026-05-04)

Subcommands `node2vec`, `betweenness`, `resistance`, `curvature`, `joint`.
Headline numbers on proof-length regression (target = log1p(tactic_count),
n=57,601 theorems, 80/20 hash split):

| Feature set | Test R² | Test ρ |
|---|---|---|
| degree | 0.506 | 0.711 |
| spectral (low10+high10) | 0.003 | 0.052 |
| **node2vec (64-d)** | **0.162** | **0.403** |
| approx betweenness (200 sources) | 0.183 | 0.429 |
| effective resistance to top-15 hubs | 0.005 | 0.074 |
| **node2vec + degree** | **0.555** | **0.745** |
| **all combined** | **0.565** | **0.752** |

So node2vec is the geometric feature that *does* lift over degree — the
spectral failure was about the encoding, not the graph.

**Ollivier-Ricci curvature** on 3,320 sampled edges (filtered by
neighbourhood size ≤ 50): mean κ = −0.781, median −0.840, **88.7 %
negative**, 35.7 % below −1. The dep graph is hyperbolic / tree-like.
Top bottleneck edges are atypical citations between semantically
distant theorems.

**Top hubs by indegree** (from the resistance subcommand): `rfl`
(2,645), `Eq.symm` (1,493), `mul_comm` (1,462), `mul_assoc` (1,267),
`mul_one`, `one_mul`, `add_comm`, `le_antisymm`, etc. — sane "fundamental
lemma" list, sanity check on the graph.

### `analysis/state_hypergraph.py` — state-tactic hypergraph

Built from LeanDojo `state_before` / `state_after`:
- 261,655 single-goal nodes (multi-goal `state_after` blobs split per `case`)
- 261,107 hyperedges, **18,467 of them true multi-output**
- Output-size histogram has tail up to 17 (rcases on big sum types)

Two algorithms:
- `or-path` — bidirectional BFS on goal-only hashes; "does B's proof go
  through a state literally equal to A's initial goal?".
- `discharge` — AND/OR DFS with memo, A as oracle; "can B be closed if
  every leaf is in {A, no goals}?".

Within-theorem sanity check passes (state→no_goals along the recorded
proof). Random theorem pairs: 0.1% reachable. Proof-DAG edges (B cites A):
2.5% reachable; conditioned on the citation tactic head: `exact` 11%,
`refine` 9.3%, `apply` 2.5%, `rw` 0.6%. **The state graph and the proof
DAG answer different questions** — the proof DAG counts every citation,
the state graph only counts citations where the goal goes through A.

Useful next moves: goal canonicalisation (alpha-rename, sort hyps,
normalise universes); subterm matching for `rw`-style uses;
hypothesis-context matching for the real oracle case.

### `analysis/kimina_eval_cuda.py` — CUDA/vLLM Kimina runner

GPU `generate` (one batched vLLM call, `SamplingParams(n=samples)`,
`--tensor-parallel-size`, `--gpu-memory-utilization`, bf16 default) and a
decoupled CPU-friendly `verify` pass that uses `lake env lean`. Reports
sample-level pass and theorem-level `pass@n`. Use this for the actual
GPU run; the older `kimina_eval.py` is a simpler one-shot alternative.

### `analysis/overnight_geometry.py` — proof-DAG pipeline

One-stop script. Subcommands:

```
python3 analysis/overnight_geometry.py build-deps              # parse LD → edges
python3 analysis/overnight_geometry.py path --goal X --oracle Y
python3 analysis/overnight_geometry.py example-paths           # 3 hardcoded
python3 analysis/overnight_geometry.py spectral --k 32         # Lanczos-style
python3 analysis/overnight_geometry.py post-kimina-manifest \
    --mathlib-dir <path-to-Mathlib4> --verify-sorry
python3 analysis/overnight_geometry.py kimina-prompts
python3 analysis/overnight_geometry.py post-kimina-anchors
python3 analysis/overnight_geometry.py report
```

Sibling scripts:
- `analysis/spectral_classifier_sweep.py` — logreg+MLP over the spectral CSV.
- `analysis/kimina_eval.py` — Kimina whole-proof runner. Needs vLLM/transformers
  and a Mathlib checkout. Honors `--skip-lean`.

The Lanczos-style routine in `overnight_geometry.spectral` does subspace
iteration on the *normalised adjacency*. Largest k eigvals → "low" features.
Smallest (most negative) k → "high" features (1 - λ are top of normalised
Laplacian). Currently k=10 by default; `spectral_features.csv` was written
with k=32 each side (146 MB).

## Negative result: spectral coords ≠ category

`results/spectral/classifier_sweep.json`:

| Feature spec        | Best acc | Best macro-F1 |
|---------------------|----------|----------------|
| majority baseline   | 0.165    | 0.011          |
| degree only         | 0.172    | 0.019          |
| **namespace prior** | **0.737**| **0.753**      |
| low10               | 0.167    | 0.022          |
| high10              | 0.166    | 0.030          |
| low10+high10        | 0.166    | 0.031          |
| low32               | 0.165    | 0.032          |
| low32+high32        | 0.166    | 0.025          |
| low10+degree (MLP)  | 0.177    | 0.021          |
| low32+high32+degree | 0.174    | 0.022          |

So no spectral feature mix beats the trivial "first dotted prefix of the
name" baseline, and most do not beat majority. The namespace baseline is a
strong cheat — `Algebra.foo`'s top-level dir is overwhelmingly `Algebra`.
**Don't promise the PI that the eigencoords predict category. They don't.**

If we want the spectral story to be useful at all, the right tests are:
- Link prediction (does it know edges from non-edges?).
- Edge category from concatenated endpoint features.
- Distance in spectral space ≈ tactic-level proof similarity.

## Path-finding semantics

`find_path(goal=B, oracle=A)` runs BFS over `source → target` =
`theorem → premise`. So it walks B's ancestors. If A is in that ancestor
closure within `--max-depth`, you get a path. **This re-traces an existing
proof**; it does not invent new ones. Trivial 1-edge results are expected
when B literally cites A.

Hand-picked examples in `results/paths/example_paths_manifest.json` are all
single-edge — they are sanity checks, not findings. For real numbers, run
the random-pair sweep (added 2026-05-03).

## Conventions / gotchas

- Always use `uv` for Python; the project has both `.venv` and `.myvenv`.
- The user's PI cares about *clear, honest writeups* even when results are
  negative. Frame negative findings as findings.
- Don't quietly drop the `UNKNOWN` category from analyses — count and
  report it.
- The `category` function only matches `Mathlib/<Top>/...` paths; anything
  outside (e.g. `Init/...`, `Std/...`) becomes `UNKNOWN`.
- BFS in `find_path` uses a `parent` map keyed by node, so it returns
  *some* shortest-edges path, but tactic-index ordering inside that
  path is just whatever BFS hit first.
- The graph is treated as undirected when computing the spectral
  decomposition (sorted endpoint pairs deduped) but directed for path
  finding.
